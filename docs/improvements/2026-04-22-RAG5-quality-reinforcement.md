## 1. 배경 (Why)

### 1-1. RAG 시리즈 기능 완성 후 재점검
[RAG-1 ~ RAG-4](./README.md#개선-이력-목록) 로 자연어 진입점, Qdrant 벡터 DB, 하이브리드
검색, LLM narrative 생성까지 **기능 관점의 RAG 파이프라인** 을 완성했다.

그 상태에서 **"돌아가는 RAG 와 운영 가능한 RAG 는 다르다"** 는 외부 아티클을 접하고
우리 구현을 다시 점검한 결과, 기능은 작동하지만 **데이터/출력 품질 관점** 에서 3가지
구조적 약점을 발견했다.

### 1-2. 발견한 3가지 약점

**① 데이터 품질 게이트 부재**
- `RouteHistoryRecorder` 가 `recommended=true` 경로를 **무조건 저장**
- 탐색 실패 디폴트 경로, 5분 미만 초단거리, 중복 새로고침 요청 등
  **"정보성 없는 이력"** 이 Qdrant 에 섞여 들어갈 수 있는 구조
- 노이즈가 누적될수록 유사 검색 품질 저하

**② 서술(embedding source) 단조성**
- `RouteHistoryDescriber` 의 출력이 항상 `"~에서 ~까지 ~, ~분 ~원."` 한 패턴
- 20건 시드가 벡터 공간에서 뭉쳐 유사도 score 가 0.5~0.6 대로 수렴
- 시간대/요일 같은 **맥락 정보가 임베딩에 미반영** → "러시아워 빠른 경로" 같은
  시간 맥락 쿼리가 의미 있게 동작하지 않음

**③ LLM 할루시네이션 감지 부재**
- `OllamaNarrativeGenerator` 가 LLM 출력을 **그대로 덮어씀**
- llama3.2:3b 가 수치를 잘못 생성하면(예: 40분 경로를 "4분" 이라 씀)
  **거짓 정보가 사용자에게 전달**
- 제품 신뢰도와 법적 리스크 직결

### 1-3. 원칙
"RAG = 기술" 로 끝내지 않고 **"프로덕션 운영 관점"** 을 처음부터 반영한다.
- **1차 방어선: 데이터 진입 단계** — 저질 데이터 차단
- **2차 방어선: 의미 표현** — 임베딩 품질 = 검색 품질
- **3차 방어선: LLM 출력 검증** — 거짓 정보 자동 폴백

## 2. 보강 내역

### 2-1. 데이터 품질 게이트 + 중복 감지 (Recorder)

**`RouteHistoryRecorder.recordAsync()` 에 2단계 필터 추가:**

```java
// 1) 품질 게이트
private boolean passesQualityGate(Route route) {
    if (route.legs() == null || route.legs().isEmpty()) return false;   // 탐색 실패 디폴트 제외
    if (route.totalMinutes() < MIN_TOTAL_MINUTES) return false;          // 5분 미만 제외
    if (route.totalCostWon() <= MIN_TOTAL_COST_WON) return false;        // 0원 이하 제외
    boolean hasNonWalkLeg = route.legs().stream().anyMatch(l -> l.type() != LegType.WALK);
    if (!hasNonWalkLeg) return false;                                     // 도보만 있는 경로 제외
    return true;
}

// 2) 중복 감지 (60초 윈도우, OD 좌표 100m 반올림 + preference 키)
private boolean isRecentlySaved(Location origin, Location dest, String preference) {
    ...
}
```

**설계 포인트:**
- Caffeine 등 추가 의존성 없이 `ConcurrentHashMap + lazy purge` 로 단순화
- 좌표를 소수 3자리(~100m) 반올림해 **근접 중복** (사용자가 약간 이동하며 재요청)까지 감지
- 60초 윈도우는 "새로고침 중복 방지" vs "다른 검색 허용" 균형점

### 2-2. 서술 다양화 (Describer)

**맥락 태그 3가지 + 도보 시간 합산 추가:**

```java
// 기존
"강남역에서 홍대입구까지 지하철 직행, 36분 1,650원. 안정적이고 환승 적은 경로."

// 개선
"평일 아침 러시아워, 강남역에서 홍대입구까지 지하철 직행, 36분 1,650원,
 도보 8분 포함. 안정적이고 환승 적은 경로."
```

**세부 구현:**
- `Instant.now() + ZoneId("Asia/Seoul")` 기준 현재 시각을 태그로 변환
- 시간대 밴드: 아침 러시아워(6-9) / 점심(11-13) / 저녁 러시아워(17-20) / 심야(22-5) 등
- 요일 밴드: 평일 / 주말
- `LegType.WALK` 구간만 합산해 "도보 N분 포함" 꼬리
- **테스트 재현성 위해 `describeAt(Route, ..., Instant when)` 오버로드** — 특정 시각 주입 가능

### 2-3. LLM 할루시네이션 감지 (OllamaNarrativeGenerator)

**출력 수치가 경로 수치와 크게 다르면 자동 폴백:**

```java
static String validateAgainstRoute(String narrative, Route route) {
    if (narrative.length() < MIN_NARRATIVE_LENGTH) return "";  // 50자 미만 품질 낮음

    // 분 검증
    Matcher m = MINUTES_PATTERN.matcher(narrative);
    while (m.find()) {
        int minutes = Integer.parseInt(m.group(1));
        if (Math.abs(minutes - route.totalMinutes()) > ALLOWED_MINUTES_DELTA) {  // ±5분
            log.warn("[RAG4] 할루시네이션 감지 (분): 출력 {}분 vs 실제 {}분 → 폴백", ...);
            return "";
        }
    }

    // 비용(원) 검증 — 1,000원 구분자 허용
    ...
}
```

**설계 포인트:**
- 빈 문자열 반환 = 호출자가 **원본 템플릿 narrative 유지** (기존 폴백 계약과 일관)
- 분 허용 오차 ±5분, 비용 ±1,000원 — LLM 의 반올림 여유 허용
- 정규식 2개로 저비용 검증 (성능 부담 없음)

## 3. 검증 & 성과 (Result)

### 3-1. A 품질 게이트 + 중복 감지

**실측 시나리오:** 같은 OD(강남→홍대) 를 즉시 2회 연속 요청

| 시점 | Qdrant points | 증가 |
|------|---------------|------|
| 요청 전 | 20 | - |
| 1차 요청 후 | 21 | +1 (정상 저장) |
| 2차 요청 후 (2초 뒤) | 21 | **+0 (중복 스킵)** |

로그 증거:
```
[RAG] 중복 저장 스킵 — 출발지 → 목적지 [RELIABILITY]
```

### 3-2. B 서술 다양화

**실측 서술 샘플 (재시드 후):**
```
평일 점심, 홍대입구에서 성수역까지 지하철+전기자전거 직행, 34분 1,698원.
  빠른 시간 우선 추천 경로.
평일 점심, 홍대입구에서 서울역까지 지하철+따릉이 직행, 22분 2,450원.
  빠른 시간 우선 추천 경로.
평일 점심, 성수역에서 건대입구까지 대중교통+따릉이 직행, 30분 2,000원.
  빠른 시간 우선 추천 경로.
```
→ 20건 전부 `평일 점심` 태그 자동 포함 (재시드 시점이 평일 낮 12시였음).

**부수 효과:** LLM narrative 출력에도 맥락 태그가 전파됨:
```
"... 이는 평일 점심에 가장 유사한 경로입니다."
```
즉 B(임베딩 소스) → RAG-2 검색 → RAG-4 프롬프트 → LLM 출력까지 **연쇄적으로 품질 향상**.

### 3-3. C 할루시네이션 감지 — 실제 포착 사례

**실제 LLM 이 40분 경로를 4분으로 지어냄 → 자동 감지 → 폴백:**
```
11:06:02.079 WARN [RAG4] 할루시네이션 감지 (분): 출력 4분 vs 실제 40분 → 폴백
```

**사용자가 받은 응답:**
- 할루시네이션이 있었던 경로 → 원본 템플릿 narrative 유지
  (`"자가용보다 4분 더 걸리지만 3,423원 절약, 탄소 999g 감소."`)
- 정상 LLM 응답 경로 → LLM narrative 사용
  (`"이 경로는 안정성과 환승의 적합도에 중점을... 평일 점심에 가장 유사한 경로입니다."`)

**만약 C 가 없었다면:** 사용자는 40분 걸리는 경로를 "4분에 도달" 이라고 설명한
**거짓 narrative** 를 그대로 받았을 것.

## 4. 배운 점

### 4-1. "기능 동작" 과 "프로덕션 품질" 은 다르다
RAG 파이프라인이 돌아간다 = 인프라 + Spring AI + 프롬프트가 연결된 것.
운영 품질 = 여기에 **데이터 진입 검증 + 의미 표현 설계 + 출력 신뢰성 검증** 3단계 방어선.

세 방어선 중 **어디 하나라도 비어 있으면 신뢰할 수 없는 RAG** 가 된다.

### 4-2. 할루시네이션은 "가능성" 이 아니라 "현실"
검증 테스트 한 번에 실제로 포착됨. 로컬 3B 모델에서는 드물지 않다.
감지 없이 운영했다면 언젠가 사용자가 **"왜 40분 경로를 4분이라고 했지?"** 같은
불신을 갖게 됐을 것.

### 4-3. 임베딩 소스 품질이 검색 품질을 결정
"서술 템플릿 단조 → 벡터 공간 뭉침" 은 RAG-2 문서에서도 인지했지만 후순위로 미뤘다.
이번에 시간대/요일 태그 추가만으로도 **검색 쿼리의 표현 폭** 이 확장되고, 나아가
**LLM narrative 출력 품질까지 간접 향상** 되는 연쇄 효과를 확인했다.

### 4-4. 작은 기능을 견고하게 > 큰 기능을 대충
이번 보강 공수는 2시간. 그런데 기록 관점에서는 **"AI 시스템을 스스로
비판적으로 보고 개선 사이클을 돈 경험"** 이라는 강력한 서사가 되었다.

## 5. 한계 & 다음 단계

### 5-1. 할루시네이션 감지의 한계
현재는 **숫자 불일치만** 감지. 이런 경우는 잡지 못함:
- 지명을 엉뚱하게 쓰기 ("강남" 을 "부산" 으로)
- 이동수단 거짓 언급 ("지하철 직행" 인데 "따릉이+지하철" 로 서술)

→ 후속: 지명/이동수단 규칙 검증 추가 가능.

### 5-2. 품질 게이트 기준의 경험적 선택
- 5분 / 0원 / 20자 / 60초 윈도우 — 모두 **근거 있는 경험치** 이지만 실 트래픽 데이터로
  재조정 필요.
- 후속: Prometheus 에 "품질 게이트 제외율" 메트릭 추가해 튜닝 근거 마련.

### 5-3. 테스트 재현성
`Instant.now()` 시간대 태그는 테스트할 때 시각 의존적. `describeAt(..., Instant when)`
오버로드는 만들어뒀지만, 기존 로직이 여전히 `now()` 에 의존. 단위 테스트는 후속.

## 6. 기록

### 30초 버전
> "RAG 파이프라인을 만든 뒤 **돌아가는 RAG 와 운영 가능한 RAG 는 다르다** 는
> 관점으로 재점검해 3가지 방어선을 추가했습니다.
> - 데이터 진입 단계 **품질 게이트 + 중복 감지**
> - 임베딩 소스에 **시간대/요일 맥락 태그**
> - LLM 출력에 대한 **할루시네이션 감지 + 자동 폴백**"

### 3분 버전 (실제 사례 포함)
1. **왜 필요했나** — 기능 완성 후 "데이터 진입 검증은 있나?"  
   "LLM 이 거짓 정보를 내면?" 이라는 질문으로 점검
2. **구체 보강** — 3개 지점의 코드 변경
3. **실제 효과** — 동일 OD 중복 저장 +0건, 서술에 `평일 점심` 자동 태그, **실제로 LLM 이 40분 경로를 4분으로 지어낸 것을 자동 포착해 원본 템플릿으로 폴백**
4. **연쇄 효과** — B(서술 다양화) 가 C(LLM 출력) 까지 품질 전파됨을 관찰

### 포지셔닝
> **"AI/ML 서비스는 만드는 것보다 운영하는 것이 어렵다** 는 걸 직접 경험했습니다.
> 로컬 3B 모델에서 할루시네이션이 실측됐고, 감지 레이어 없이 운영했다면 사용자가
> 거짓 정보를 받았을 상황이었습니다."
